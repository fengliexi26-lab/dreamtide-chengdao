# 《梦潮：承道》PVE 卡牌体系设计 v1

## 一、重建目标

当前 `data/cards/cards_v0.json` 属于旧 PVP / 原型测试卡池。它帮助项目完成了早期规则验证，但已经不适合作为正式 PVE 肉鸽卡池继续局部修补。

当前主要问题：

- 卡牌归属不清，通用牌、道主牌、敌人牌和原型牌混在一起。
- 道主之间牌组差异不足，初始牌组主要靠重复旧测试牌拼接。
- 大量卡牌只有展示文本，没有代码支持。
- 人物牌、道痕、命器、敌人单位与普通手牌混在同一文件。
- 境界要求、命源要求和阵势费用仍残留旧 PVP 规则。
- `effect_text` 与实际结算能力不一致。
- 卡牌效果缺乏统一数据结构。
- 没有通用牌、道途共享牌、道主专属牌的明确分层。

新版目标：

- 每位道主形成真正不同的职业牌组。
- 少量通用牌补足基础攻击、防御、抽牌和简单功能。
- 道途共享牌形成跨职业构筑。
- 道主专属牌决定职业核心。
- 卡牌效果由结构化数据驱动。
- 显示文本不再承担效果判定。
- 只允许已实现效果进入正式玩家牌池。

## 二、卡牌归属层级

正式字段：`owner_scope`

### 1. universal

- 所有道主均可使用。
- 提供基础攻击、防御、抽牌和简单功能。
- 强度稳定，但不应成为构筑上限。
- `owner_ids` 通常为空数组。

### 2. shared

- 只有符合 `owner_ids` 或 `pool_tags` 的道主可获得。
- 按道途、侧性和机制共享。
- 不按照“一世 / 三君 / 五不归”机械划分。
- 示例：守界、阵势、梦夜、归葬、回潮、预见等机制池。

### 3. exclusive

- 仅属于指定道主。
- 直接服务该道主被动和核心玩法。
- 应构成每名道主初始牌组和奖励池主体。
- `owner_ids` 通常只包含一个道主 id。

### 4. token

- 战斗中临时生成。
- 不进入普通奖励池和初始牌组。
- 可由卡牌、敌人、事件或 Boss 生成。

### 5. enemy_only

- 只供敌人或 Boss 使用。
- 不进入玩家牌池。
- 不包含玩家道主 `owner_ids`。

## 三、初始牌组构成

每位道主初始牌组暂定 12 张。

推荐比例：

- 道主专属牌：6-7 张
- 道途共享牌：3-4 张
- 通用牌：1-2 张

要求：

- 开局即可体现职业差异。
- 不允许三位道主使用大面积相同基础卡。
- 通用牌只负责基础功能。
- 专属牌必须可以稳定触发本职业被动。
- 每套初始牌组至少包含攻击、防御和职业核心手段。
- 初始牌组不得包含未实现效果牌。
- 初始牌组不得包含道痕、命器、人物牌和敌人单位。

## 四、奖励池构成

普通战斗奖励推荐倾向：

- 道主专属牌约 55%
- 兼容道途共享牌约 30%
- 通用牌约 15%

说明：

- 不要求严格按百分比实现。
- 专属牌应为奖励池主体。
- 通用牌不得成为所有职业的最优解。
- 不兼容的 `shared` / `exclusive` 卡不得出现在奖励中。
- 后续 `RunState` 根据 `selected_daomaster_id` 和 `dao_tags` 过滤奖励池。

## 五、卡牌类型

正式 PVE 卡牌类型建议使用 `card_type`。

### 1. daofa

- 普通即时卡。
- 覆盖攻击、防御、抽牌、状态、回潮和功能效果。

### 2. chengdao

- 召唤承道兽。
- 打出后进入战场。
- 承道兽拥有攻击、生命和死亡去向。

### 3. formation

- 法阵。
- 战斗内持续效果。
- 只有正式持续效果系统完成后才进入 active 牌池。

### 4. domain

- 域界。
- 改变本场战斗规则。
- 通常每场最多存在一个。

### 5. trap

- 伏法。
- 延迟触发或条件反制。
- 只有触发系统完成后才进入 active 牌池。

### 类型迁移说明

- `character` 不进入普通牌组。
- `dao_mark` 改为遗物系统。
- `artifact` / `life_artifact` 改为命器 / 装备系统。
- `enemy` 单位不得混入玩家牌池。

## 六、标准卡牌数据结构

推荐 JSON 结构：

```json
{
  "id": "zaiheng_jieyue",
  "name": "界约",
  "card_type": "daofa",
  "subtype": "skill",
  "owner_scope": "exclusive",
  "owner_ids": ["zaiheng_jun"],
  "pool_tags": ["衡", "序", "守界", "阵势"],
  "rarity": "common",
  "cost": 1,
  "target_type": "self",
  "effects": [
    {
      "type": "gain_formation",
      "value": 6,
      "target": "self"
    }
  ],
  "keywords": [],
  "dao_tags": ["衡界"],
  "side": "order",
  "starter_allowed": true,
  "reward_allowed": true,
  "implementation_status": "implemented",
  "effect_text": "获得6点阵势。",
  "flavor_text": ""
}
```

字段说明：

- `id`：稳定唯一 id，不随显示名改动。
- `name`：显示名。
- `card_type`：正式 PVE 卡牌类型。
- `subtype`：攻击、技能、召唤、持续、特殊等细分类。
- `owner_scope`：`universal` / `shared` / `exclusive` / `token` / `enemy_only`。
- `owner_ids`：兼容道主 id 列表。
- `pool_tags`：奖励池和共享池过滤标签。
- `rarity`：稀有度。
- `cost`：道息费用。
- `target_type`：目标类型。
- `effects`：实际结算效果数组。
- `keywords`：规则关键词。
- `dao_tags`：世界观道脉标签。
- `side`：秩序、混沌、中立等侧性。
- `starter_allowed`：是否允许进入初始牌组。
- `reward_allowed`：是否允许进入奖励池。
- `implementation_status`：实现状态。
- `effect_text`：展示文本。
- `flavor_text`：风味文本，不参与效果判定。

## 七、效果数据结构

正式规定 `effects` 为数组。

第一批基础效果类型建议：

- `deal_damage`
- `gain_formation`
- `draw`
- `gain_daoxi`
- `gain_reflux`
- `reduce_reflux`
- `apply_status`
- `summon`
- `discard`
- `exhaust`
- `retain`
- `heal`
- `modify_beast_attack`
- `modify_beast_life`

每个效果至少包含：

- `type`
- `value`
- `target`

根据需要可增加：

- `count`
- `duration`
- `condition`
- `scaling`
- `status_id`
- `summon_card_id`

示例：

```json
{
  "type": "deal_damage",
  "value": 7,
  "target": "enemy"
}
```

```json
{
  "type": "summon",
  "target": "self",
  "summon_card_id": "token_zaiheng_order_guard",
  "count": 1
}
```

要求：

- `effect_text` 只用于展示。
- `BattleScene` 不应继续通过 `effect_text` 搜索普通数值效果。
- `keywords` 可以用于凝梦、消耗等规则性关键词。
- 实际伤害、阵势和抽牌必须来自 `effects`。

第一版迁移时可以暂时同时保留旧字段：

- `damage_tier`
- `formation_gain`
- `draw_count`

这些属于兼容字段，将逐步迁移到 `effects`。

## 八、关键词体系

### 已实现或近期可进入 active 的关键词

#### 1. 凝梦

- 回合结束时不被自动弃置。
- 当前已由 PVE 回合流支持。

#### 2. 消耗

- 使用后进入 `exhaust_pile`。
- 当前已由 PVE 三堆系统支持。

### 未来关键词

#### 3. 守阵

- 允许部分阵势跨玩家回合保留。
- 尚未实现，不得进入 active 结算效果。

#### 4. 回响

- 本场战斗满足条件后可以再次触发或获得额外效果。
- 暂时只定义，不急于实现。

#### 5. 送归

- 与承道兽死亡相关。
- 暂时作为负棺僧机制标签。

#### 6. 剪除

- 移除增益、卡牌或成长效果。
- 后续服务断春夫人和绝岸古尊。

#### 7. 预见

- 查看未来抽牌或敌人意图。
- 后续服务绝岸古尊。

关键词规则：

- 未实现关键词不得进入 active 卡牌效果。
- 卡牌名称或 `flavor_text` 中出现关键词文字，不代表实际拥有该关键词。
- 只有 `keywords` 字段或明确结构化效果才代表规则含义。

## 九、费用与数值基线

当前基础规则：

- 每回合基础道息 3。
- 每回合固定抽 5。
- 手牌上限 10。
- 玩家基础命源约 70。
- 敌人基础生命约 60-100。
- 承道兽最多 3 只。

第一轮数值基线：

### 通用牌

- 0 费：极低效果，通常带消耗或明显限制。
- 1 费攻击：5-8 伤害。
- 1 费阵势：5-7 阵势。
- 1 费抽牌：抽 1，或带条件抽 2。
- 2 费攻击：11-16 伤害。
- 2 费防御：10-14 阵势。
- 复合牌的单项数值必须低于纯功能牌。

### 道主专属牌

- 可以比通用牌略高效。
- 高效率应依赖职业条件、被动或风险。
- 不允许无条件全面优于所有通用牌。

## 十、承道兽设计规范

承道兽是本项目核心特色，应区分：

- 通用承道兽
- 道途共享承道兽
- 道主专属承道兽
- token 承道兽
- enemy_only 单位

基础字段：

- `summon_id`
- `attack`
- `life`
- `side`
- `dao_tags`
- `chengdao_kind`
- `death_destination`
- `abilities`
- `is_special`

规则：

- 1 费普通承道兽建议攻击 2-5、生命 5-12。
- 2 费普通承道兽建议攻击 5-8、生命 9-17。
- 秩序兽通常更耐久。
- 混沌兽通常攻击更高并增加回潮。
- 特殊承道兽通常死亡进入消耗堆。
- 普通承道兽死亡进入弃牌堆。
- `enemy_only` 单位不得进入玩家奖励池。

## 十一、稀有度

建议：

- `basic`：只用于初始牌组或基础系统。
- `common`
- `uncommon`
- `rare`
- `unique`

规则：

- `basic` 通常不进入普通奖励池。
- `unique` 每个 Run 通常只能拥有一张，或由特殊事件获得。
- 道主核心能力不应全部放在 `rare`，初始牌组必须能工作。

## 十二、卡牌升级

第一版只设计规则，不实现。

升级方式建议：

- 数值升级：伤害 / 阵势增加。
- 费用升级：费用降低。
- 关键词升级：获得凝梦、移除消耗等。
- 条件升级：降低触发门槛。
- 效果升级：抽牌或额外效果增强。

每张卡未来可以包含：

- `upgrade_id`
- `upgraded_name`
- `upgraded_effects`
- `upgraded_cost`
- `upgraded_effect_text`

升级不能直接修改原始 JSON 实例，应通过 `card_instance` 或 `upgrade_state` 表示。

## 十三、三位开放道主卡牌方向

### 宰衡君

- 主要资源：阵势、道行、稳定场面。
- 主要防御方式：高效获得阵势，未来可通过守阵保留部分阵势。
- 主要输出方式：稳定小额攻击、无伤收益、承道兽持续攻击。
- 承道兽倾向：秩序、守界、耐久型。
- 构筑风险：过度防御导致输出不足。
- 与被动联动：专属牌应稳定制造“每回合第一次获得阵势”的触发窗口。
- 方向关键词：阵势、衡量、无伤收益、册命、界约、秩序承道兽。

### 织夜君

- 主要资源：凝梦牌、保留手牌、延迟收益。
- 主要防御方式：留宵带来的阵势、残世保护、延迟减伤。
- 主要输出方式：梦夜道法、延迟伤害、保留牌积累后爆发。
- 承道兽倾向：梦夜、低攻高功能、保护濒死单位。
- 构筑风险：保留过多导致手牌拥挤，前期节奏偏慢。
- 与被动联动：专属牌应让玩家有理由保留 1-3 张凝梦牌。
- 方向关键词：凝梦、保留、夜幕、延迟伤害、残世保护、梦夜承道兽。

### 负棺僧

- 主要资源：承道兽死亡、消耗堆、归葬收益。
- 主要防御方式：承道兽分担压力、死亡后收益、归葬循环。
- 主要输出方式：承道兽攻击、死亡触发伤害、消耗牌爆发。
- 承道兽倾向：短寿、特殊、死亡有价值。
- 构筑风险：缺少承道兽时被动空转，过度消耗导致循环变薄。
- 与被动联动：专属牌应制造“己方承道兽死亡后下回合获益”的计划感。
- 方向关键词：承道兽死亡、送归、消耗、弃牌堆、特殊承道兽、归葬收益。

## 十四、通用牌设计原则

不同道主之间应存在通用卡牌。

但通用牌应遵守：

- 初始牌组中只占 1-2 张。
- 提供基础攻击、防御和简单功能。
- 不直接替代专属牌。
- 不应无条件拥有高效率复合效果。
- 不直接为某一被动提供最强触发。
- 奖励池中占比较低。
- 用于修补构筑缺口。

通用牌的价值是“让 Run 不崩”，不是“定义职业上限”。

## 十五、道途共享牌原则

共享牌通过 `pool_tags` 和 `owner_ids` 控制。

示例：

- 守界 / 阵势：宰衡君、守灯侯。
- 梦 / 夜 / 留存：织夜君，以及未来部分梦道角色。
- 归 / 葬 / 舍弃：负棺僧、部分绝渡君卡池。
- 潮 / 海 / 回潮：饮潮王和混沌方向。
- 名 / 册 / 记载：缺名公、宰衡君少量交叉。
- 生机 / 枯荣 / 剪除：断春夫人。
- 预见 / 剪枝 / 定世：绝岸古尊。

共享关系必须服务玩法，不按人物层级机械划分。

## 十六、实现状态

`implementation_status` 统一为：

- `implemented`
- `partial`
- `planned`
- `unsupported`
- `legacy`

只有以下组合可以进入正式 active 玩家牌池：

- `implementation_status = implemented`
- `starter_allowed = true` 或 `reward_allowed = true`
- `owner_scope` 与当前道主兼容

`partial` 卡可以保留数据，但不得默认进入初始牌组。

`legacy` 卡只用于旧数据兼容，不进入 v1 PVE 主流程。
